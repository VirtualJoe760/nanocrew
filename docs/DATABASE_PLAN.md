# Nanocrew Database Plan

Goal: give Nanocrew the persistence layer stephen-lawyer has, but **multi-tenant** —
every creator builds their own store/website through the app, sells auto-fulfilled
clothing, and is billed via Stripe in the Next.js web portal.

---

## 1. Reference — stephen-lawyer's implementation (what we're mirroring)

**Stack:** Drizzle ORM `0.38` + `postgres-js` → Neon Postgres · NextAuth v5 (`@auth/drizzle-adapter`) · Stripe `17` · Resend (email auth + transactional).

**Files:**
- `drizzle.config.ts` — dialect `postgresql`, migrations → `src/db/migrations`, url = `DATABASE_URL_UNPOOLED ?? DATABASE_URL` (Neon pooled vs direct).
- `src/lib/db.ts` — `postgres(url,{ prepare:false, max:5 })` → `drizzle(client,{ schema })`; a `Proxy` throws if `DATABASE_URL` is missing (so build doesn't crash without a DB).
- `src/db/schema.ts` (339 lines) — all tables + relations + `$inferSelect` type exports.
- `src/db/migrations/0000–0004` — generated by `drizzle-kit generate`; applied by `drizzle-kit migrate`.

**Schema (single store):**
- **Auth:** `users`, `accounts`, `sessions`, `verification_tokens` (NextAuth shape).
- **Commerce:** `addresses`, `drops`, `products`, `variants`, `orders`, `order_items`, `newsletter`.
- **Design generator:** `catalogues` → `designs` → `compositions` → `canvas_nodes`.
- **Enums:** `order_status`, `product_category` (tees/hoodies/hats/accessories), `composition_status` (generating/draft/approved/published/failed).

**Conventions worth keeping:** money as integer **cents** + 3-char currency; **jsonb** for flexible shapes (`position`, `placements[]`, `shipping_address_json`); `printful_sync_*_id` columns link rows to Printful; `onDelete: cascade` down ownership chains; indexes on FKs + status; `uuid` PKs (except NextAuth's text ids).

## 2. The gap — single-tenant → multi-tenant

stephen-lawyer **is** one store. Nanocrew is a **platform of stores**. Every table that
represents content or commerce must be scoped to a **store**, and we add two new layers:

1. **Tenancy** — `creators` (app users) own `stores` (their generated websites).
2. **Creator billing** — Stripe subscriptions/Connect, driven from the web portal (NOT the mobile app, to dodge Apple IAP).

Topology decision (recommended): **one central multi-tenant Postgres**, every row scoped by
`store_id`. The mobile app's Expo Router API routes, the web portal, and each codegen'd
storefront all read the same DB filtered by store. (Alternative — a DB per store — is
operationally heavier and kills the cross-store marketplace; not recommended.)

## 3. Proposed Nanocrew schema

### 3.1 Tenancy & identity (NEW)
```
creators            -- the app users (people building stores). NextAuth `users` shape +:
  id, email(unique), name, image, email_verified, created_at
  (auth tables: accounts, sessions, verification_tokens — same as stephen-lawyer)

stores              -- one per creator website/store (the thing the app generates)
  id, creator_id→creators(owner), name, slug(unique=subdomain), custom_domain(unique,null),
  status(store_status: draft|building|live|suspended),
  theme(jsonb: colors/fonts), logo_url, favicon_url, og_image_url, tagline, description_md,
  printful_store_id(text — per-creator Printful sub-store), deployment_url, repo_ref(codegen),
  is_public(bool — marketplace visibility), sort_order, created_at, updated_at
  idx: creator_id, slug, (is_public,status)
```

### 3.2 Design generator (MIRROR stephen-lawyer, + store_id)
```
catalogues   + store_id→stores            (collections within a store)
designs      catalogue_id, store_id, prompt, cloudinary_public_id, url, thumb_url, created_by→creators
compositions catalogue_id, store_id, design_id, template_key, placement,
             position(jsonb), placements(jsonb[]), preview_url,
             status(composition_status), printful_sync_product_id, error_message, ts
canvas_nodes catalogue_id, kind, ref_id, group_id, x,y,width,height,scale,z_index, updated_at
```
(Identical to stephen-lawyer except the `store_id` scoping — lets us lift the existing
API-route logic almost verbatim.)

### 3.3 Commerce (MIRROR stephen-lawyer, + store_id)
```
products   + store_id→stores; slug unique PER store (composite uniq), printful_sync_product_id,
             name, description_md, category(text — full Printful catalog is broader than the
             4-value enum; use text or widen the enum), is_published, ts
variants   product_id, printful_sync_variant_id, sku, color, size, retail_price_cents, currency,
             in_stock, image_url
orders     + store_id→stores; customer_email, stripe_session_id, stripe_payment_intent_id,
             printful_order_id, status(order_status), subtotal/shipping/tax/total_cents, currency,
             shipping_address(jsonb), application_fee_cents(platform cut), tracking, ts
order_items order_id, variant_id, quantity, unit_price_cents, name_snapshot, variant_snapshot
addresses  end-customer addresses (optional; orders can be guest)
```

### 3.4 Creator billing (NEW — web portal)
```
subscriptions      -- creator pays Nanocrew to run their store
  id, creator_id, stripe_customer_id, stripe_subscription_id,
  plan(subscription_plan: free|pro|...), status(active|trialing|past_due|canceled),
  current_period_end, created_at, updated_at

connected_accounts -- ONLY if we route customer payments to creators (Stripe Connect)
  id, creator_id, stripe_account_id, charges_enabled, payouts_enabled, details_submitted
```

### 3.5 New enums
`store_status`, `subscription_plan`, `subscription_status` (+ keep `order_status`,
`composition_status`; replace/​widen `product_category`).

## 4. Stack & setup (mirror stephen-lawyer, inside the Expo project)

Nanocrew already serves server code via Expo Router **API routes** (`+api.ts`), so the exact
same Drizzle + postgres-js client works server-side.

1. **Provision Postgres** (recommended **Neon**, matches stephen-lawyer) → `DATABASE_URL`
   (+ `DATABASE_URL_UNPOOLED`) in `.env.local`. *(Needs Joe — account/credentials.)*
2. Add deps: `drizzle-orm postgres` + dev `drizzle-kit`. Scripts `db:generate|migrate|studio`.
3. Create `drizzle.config.ts`, `src/db/schema.ts`, `src/lib/db.ts` (copy stephen-lawyer's
   client pattern incl. the Proxy fallback).
4. `npm run db:generate` → `npm run db:migrate`.
5. Wire the **Design tab** to persist (catalogues/designs/compositions/canvas_nodes) — this
   replaces the current in-memory state (the "no collections, nothing survives reload" gap).
6. Web portal (separate Next.js) shares the same `DATABASE_URL` for **Stripe billing** +
   the **marketplace** (query `stores` where `is_public` + `status=live`).

## 5. Billing architecture (Stripe via the web portal)

Two models, not mutually exclusive:
- **A. Creator subscription** — creators pay Nanocrew monthly to host/run their store
  (`subscriptions` table). Simple; predictable.
- **B. Per-sale commission (Stripe Connect)** — end customers pay on the creator's store;
  Connect splits each charge (creator gets paid out, Nanocrew keeps `application_fee_cents`).
  Needs `connected_accounts` + Connect onboarding in the web portal.

All Stripe lives in the **web portal** (checkout, customer portal, webhooks →
`STRIPE_WEBHOOK_SECRET`). The mobile app never touches Stripe (Apple IAP avoidance).

## 6. Decisions (LOCKED 2026-06-10 by Joe)

1. **Billing model: BOTH** — creator subscription (Stripe Billing) AND per-sale commission
   (Stripe Connect, `application_fee_cents`). Sequence the build: Billing first, Connect
   onboarding second — but the schema carries both from day one.
2. **Stack: SUPABASE** — Postgres + Auth + Storage in one provider. Drizzle ORM against
   Supabase's Postgres (use the **pooled** connection string for serverless API routes,
   the direct string for migrations). Supabase Auth for creator sign-in (Expo SDK).
3. **Topology: central multi-tenant DB** (one Postgres, `store_id` scoping everywhere).
4. **Studio model: shared structural skeleton + generated brand design system.** All stores
   follow the stephenlawyer.clothing layout format (ticker/hero/drops/shop/product/editorial)
   but vary WIDELY in design: minimalist / 3D / black-and-white / animated color / motion
   transitions. The brand interview collects deep identity data — name, colors, logo, AND
   character data (favorite movie lines, personality) — stored as a **brand profile** that
   drives both the copy and a rich generated **design-system config** (palette, type, texture,
   motion language), not just a color swap. Add a `brand_profile` jsonb + `design_system`
   jsonb to `stores`.
5. **Seed content:** our own designer-published products + Stephen Lawyer imported as the
   flagship brand + a few Studio-generated AI demo brands.
